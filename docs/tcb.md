# Trusted computing base

**Definition.** TCB = code whose defect could (a) let unauthenticated/untrusted content execute, (b) defeat a
verification, rollback or revocation decision, (c) corrupt measurements, or (d) break the memory-protection boundary
(W^X). It is defined by *role*, not by which stage a file is linked into.

**Method.** `scripts/tcb_report.py` parses the linker maps of both stages (so `--gc-sections` is already applied: only
code that survives linking is counted), classifies each object as TCB / third-party TCB / non-TCB, and sums
`.text + .rodata + .data`. `.bss`/stack, host tools, tests and the update manager (not linked into the boot path) are
excluded. Output: `docs/tcb-report.md` (regenerated by `make verify`; `make tcb` prints it).

**Honest reading of the result.**
* The numbers are small in absolute terms, but almost the whole linked image is TCB. The design **does not** partition
  the TCB (e.g. DTB parsing, exception handling and MMU code share one trust domain with the verifier).
* Monocypher is the largest single TCB component (vendored, reviewed upstream, not reviewed by this project).
* The DTB parser runs only on *authenticated* data, but it is still before-kernel code in the same domain; a bug
  there is exploitable by whoever holds the DTB signing key, which is the correct residual risk to state.
* Earlier statements equating "TCB" with the 40 KB Stage 2 *file* were wrong: that file size includes page-alignment
  padding. Use the report.

**Not claimed:** formal minimality, isolation between components, or a TCB smaller than comparable boot stages.
